# ADR-0002: Two-Stage User Data Layer (`inbox/` Raw Dropzone → `profile/` Canonical Source of Truth)

## Status
Proposed (2026-10-29)

## Context
Professionals who want to build a portfolio rarely have their career history organized in a clean developer-friendly schema. Instead, they have a messy collection of files scattered across their computer:
- An old PDF or Word (`.docx`) resume
- A LinkedIn profile export or URL
- Loose photos, headshots, or project screenshots in high-resolution `.png`/`.jpg`/`.heic` formats
- Unstructured text notes or links to articles, Behance/Dribbble/GitHub pages, or publications

If the AI Agent reads directly from raw files and writes content straight into React components (`site/src/...`):
1. **No Single Source of Truth:** There is no clean way for the user or AI to verify what facts were extracted before generating code, increasing the risk of hallucinated or missing career data.
2. **Brittle Future Updates:** When the user wants to add a new project or job 6 months later, the AI would have to reverse-engineer hardcoded JSX components, risking accidental regression of the layout or styling.
3. **Unoptimized Media:** Raw multi-megabyte photos dropped by the user would bloat the repository and ruin Core Web Vitals (LCP/CLS) if copied directly into the site without automated resizing and `WebP` conversion.

## Decision
We will implement a **Two-Stage User Data Layer** governed by `DATA_CONTRACT.md`:

1. **Stage 1 — `inbox/` (Raw Unstructured Dropzone):**
   - A gitignored directory (except for `.gitkeep` and a short `README.md`) where the user drops any raw files: `.pdf`, `.docx`, `.txt`, `.md`, images (`.jpg`, `.png`, `.webp`), and URLs.
   - Treated as **read-only input** by the intake pipeline.

2. **Stage 2 — `profile/` (Canonical Structured Source of Truth):**
   - Populated and maintained by the AI via `modes/intake.md` and `scripts/intake.mjs`.
   - Contains three canonical Markdown files with strict YAML frontmatter plus an optimized asset folder:
     - `profile/_profile.md`: Canonical professional identity, bio, career timeline, projects/case studies, publications, skills, testimonials, and verified links. **Golden Rule:** Never contain fabricated facts; every entry must trace back to `inbox/` or explicit user answers during the intake gap interview.
     - `profile/_design.md`: Locked visual direction generated by `modes/brainstorm.md` (`scripts/style-picker.mjs`), storing the chosen layout archetype, color palette tokens, typography pairing, motion intensity, and section order.
     - `profile/_custom.md`: Optional user-specific overrides, custom domain notes, or persistent AI instructions that survive portfolio regeneration.
     - `profile/assets/`: Automatically resized, compressed, and converted `.webp` images with extracted dimensions (`width`/`height`) and descriptive `alt` text metadata to guarantee zero Cumulative Layout Shift (`CLS = 0`).

3. **Content-Presentation Decoupling (`profile/` → `site/`):**
   - The generated portfolio application in `site/` consumes data from `profile/` (or a build-time synchronized content layer derived strictly from `profile/`).
   - Incremental updates (`modes/add.md`) update `profile/_profile.md` and `profile/assets/` first, and `scripts/sync-check.mjs` verifies that every fact in `profile/_profile.md` is accurately reflected in `site/`.

## Consequences

### Positive
- **Zero Schema Friction for the User:** Users just drag-and-drop whatever files they already have into `inbox/`.
- **Anti-Hallucination Auditability:** Because `profile/_profile.md` is generated in Block A (`intake`) before any UI code is written in Block C (`build`), `scripts/sync-check.mjs` can deterministically verify that no fake metrics or invented employers entered the portfolio.
- **Effortless Maintenance (`modes/add.md`) & Redesigns (`modes/brainstorm.md`):** Users can add a new career milestone to `profile/_profile.md` without breaking their design in `profile/_design.md`, or completely change their visual design in `profile/_design.md` without re-uploading their resume.
- **Built-In Image Performance:** Converting raw images from `inbox/` into optimized `WebP` assets in `profile/assets/` during intake guarantees fast loading times before `site/` even builds.

### Negative
- **Two-Step File Sync Overhead:** Requires `scripts/intake.mjs` (using lightweight Node.js parsers for PDF/DOCX/images) and `scripts/sync-check.mjs` to keep `profile/` and `site/` in lockstep.

### Neutral
- Raw files inside `inbox/*` are gitignored by default so users do not accidentally push heavy raw PDFs or private unredacted documents to public GitHub repositories, while `profile/` can be versioned cleanly.

## Alternatives Considered

### Alternative 1: User Manually Fills Out a Huge `config.json` or `resume.yaml`
- **Why not chosen:** Editing deeply nested JSON/YAML syntax causes syntax errors and frustrates non-technical users.

### Alternative 2: Direct `inbox/` → Hardcoded JSX in `site/` (No Intermediate `profile/`)
- **Why not chosen:** Makes incremental updates (`modes/add.md`), design switching, and anti-hallucination verification fragile and error-prone.
